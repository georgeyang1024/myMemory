# ADR-0013 · 命中判定：按查询词实际出现，而非 BM25 分数为正

**状态**：已采纳 · 2026-09-02（实施阶段发现的缺陷修复）

## 背景

检索的初版实现用 `score > 0` 过滤结果，理由是"BM25 对完全不相关的块给 0 分"。
单元测试在小语料上直接失败：一个明确存在的匹配返回了空结果。

排查结论是 `rank_bm25` 的 `BM25Okapi` 计算方式：

```
idf = log(N - n + 0.5) - log(n + 0.5)
```

当一个词出现在超过半数 chunk 中时，`idf` 为**负**。库内的 epsilon 兜底取的是
`average_idf` 的倍数，在平均 idf 本身为负时依然为负。此时**真实命中的分数是负的**，
`score > 0` 会把它们整个丢掉。

实测：3 个 chunk 的小语料中，查询"规格汇总"的三个词 idf 均为 `-0.099`，
真实命中得分 `-0.29`，被过滤后返回空。

这不只是小语料的问题 —— 在完整语料上，任何"全部由常见词构成"的查询都会
不同程度地触发同一机制，查询词越常见，被丢弃得越彻底。

## 决策

命中判定改为：**chunk 中确实出现了至少一个查询词**。

```python
unique_tokens = set(tokenize(query))
doc_freqs = self.bm25.doc_freqs          # rank_bm25 已为每个 chunk 维护词频表
ranked = [i for i in range(len(self.chunks))
          if not unique_tokens.isdisjoint(doc_freqs[i])]
ranked.sort(key=lambda i: scores[i], reverse=True)
```

BM25 分数仍然用于**排序**，只是不再用于**判定是否命中**。

## 理由

"命中"的语义本来就是"包含查询词"，而不是"某个打分函数的输出为正"。
用分数做存在性判定，是把排序信号误用为过滤信号。

复用 `bm25.doc_freqs`（rank_bm25 已经为每个 chunk 维护的词频表）做存在性判断，
不需要额外存储 —— 内存开销为零，判定开销为 3,106 次集合相交，亚毫秒级。

## 后果

- 常见词构成的查询不再返回空结果
- 结果中可能出现负分。这是 BM25Okapi 的固有性质，分数只用于组内排序，
  其绝对值对调用方没有意义 —— 响应中保留 `score` 字段仅供人工排查
- `total_matched` 的语义是"包含至少一个查询词的 chunk 数"，
  在常见词查询下会很大（可达数千）。这是诚实的口径，不是缺陷
