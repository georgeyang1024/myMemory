# ADR-0007 · 索引生命周期：全内存 + 60 s mtime 轮询 + 原子替换

**状态**：已采纳 · 2026-09-02
**修订**：2026-09-24 —— 轮询周期改由 `config.json` 的 `poll_interval` 提供（默认 600 s），轮询覆盖全部 workspace；另增 `POST /reindex` 手动重建。见 [ADR-0017](0017-config-file-and-cli.md)。
**修订**：2026-09-24（二）—— "索引不持久化"已被 [ADR-0019](0019-index-cache-incremental.md) 取代：引入索引缓存与增量更新。

## 背景

实测 265 文件的完整冷启动构建：

| 阶段 | 耗时 |
|---|---|
| 读盘 | 0.08 s |
| 切块（3,106 chunk） | < 0.01 s |
| jieba 分词（含词典加载） | 1.68 s |
| BM25 建索引 | 0.13 s |
| **合计** | **≈ 2.2 s** |
| 单次查询 | 2 ms |
| 序列化体积 | 12 MB |

知识库是**活的**：新的会议纪要、方案稿与技术资料持续被人工放入 `raw/`。

## 备选方案

1. 启动时构建进内存，文件变更需重启服务
2. 启动构建 + 后台 mtime 轮询自动重建
3. 索引落盘持久化 + 手动 `reindex` 命令

## 决策

采用方案 2。后台线程每 60 s `stat` 一遍全部文件（实测 < 10 ms），
最大 mtime 变化则在后台完整重建，构建完成后**单条赋值原子替换**全局快照引用。

## 理由

**2.2 秒的全量重建时间是这个语料规模送来的礼物**——它意味着完全不需要增量更新的
任何复杂度，无脑全量重建即可。方案 2 是唯一吃到该红利的选项。

方案 3 在 2.2 秒重建面前是纯粹的复杂度负债：12 MB pickle 反序列化本身接近 1 秒，
省下的时间换来的是"落盘索引与源文件不同步"这个经典故障源，外加一个额外命令和
一类"忘了 reindex"的人为失误。

## 后果

- 新文件放入 `raw/` 后最长 60 s 自动生效，服务永不需要重启（间隔可通过 `MEMORY_POLL_INTERVAL` 调整）
- **并发模型无锁**：快照是不可变对象，请求路径只读取全局引用一次并在整个请求内持有。
  重建期间在途请求继续使用旧快照，Python 属性赋值的原子性是唯一同步点
- **失败策略**：后台重建抛异常则保留旧快照、记 ERROR、下轮重试。服务永不因重建失败而不可用
- 进程重启会丢失索引，需 2.2 s 重建。首次构建阻塞完成后才开始监听端口，
  因此不存在"已启动但索引未就绪"的窗口

## 补记 · 2026-09-16 · 默认间隔由 60 s 改为 3600 s

决策本身不变（方案 2、全量重建、原子替换），变的只是默认间隔。

理由：语料由人工按周期整理后成批放入，不是持续写入；60 s 的新鲜度没有对应的
真实需求，却让每台部署机每天做 1,440 次全量 `stat` 扫描——在网络挂载或
Windows 共享盘上，这项开销比在本地盘明显得多。

代价是"放进去到搜得到"的最长延迟变成 1 小时。两条逃生口径不变：
重启服务立即重建，或把 `MEMORY_POLL_INTERVAL` 调小（值本身一直是可配的）。

## 补记 · 2026-09-16 · Git 状态采集并入同一轮询

`/health` 新增的语料版本坐标（分支、提交时间、工作区脏否）没有自己的定时器，
而是挂在这条轮询线程上：每轮**先采 Git 状态，再按需重建索引**，串行执行。

理由：两者回答的是同一个问题——语料现在是哪一版。各自计时会让 `/health` 出现
"索引已经是新的、分支与脏否还停在上一版"的组合，而这两组字段本来就是用来交叉
印证的。共用间隔也意味着只有一个旋钮：`MEMORY_POLL_INTERVAL=0` 时两件事一起停。

脏否检查要遍历语料目录（实测约 1.1 s），放在这条线程上正好避开请求路径；
`/health` 只读上次采到的快照，附 `checked_at` 说明新鲜度。采集失败只记日志，
不打断索引重建——与重建失败保留旧快照是同一套 fail-soft 口径。

## 补记 · 2026-09-22 · 默认间隔由 3600 s 改为 600 s

决策本身仍不变，再次调的只是默认值：**1 小时 → 10 分钟**。

上一次调大的前提是"每台部署机各跑一个实例、语料成批放入"。现在的用法变了：
服务改成宿主上**一个常驻 HTTP 实例**供所有会话共享（见记忆库里
`claude-code/容器里MCP改走HTTP-stdio在9p上太慢.md`），编辑器里随手改一篇、
紧接着就想在会话里搜到，成了日常动作；1 小时的延迟在这种用法下等同于
"改完必须重启服务"。

开销这一侧的顾虑也小了：只有一个实例在扫，不再是 N 台 × N 个进程；
实测 117 篇语料全量重建 3.2 秒，`stat` 扫描一轮远在毫秒级。
每天 144 轮，代价可以忽略。

两条逃生口径依旧：重启服务立即重建，或用 `MEMORY_POLL_INTERVAL` 改成别的值
（含 `0` 完全关掉）——默认值变了，旋钮没变。
