# ADR-0019 · 索引缓存：启动先用缓存服务，后台增量校验

**状态**：已采纳并实施 · 2026-09-24
**取代**：[ADR-0007](0007-in-memory-index-with-polling.md) 的"索引不持久化"、
[ADR-0014](0014-write-tool-boundary.md) 的"不做增量索引"

## 背景

ADR-0007 的地基是"全量重建只要 2–3 秒"。挂载部门知识库（网络盘，约 1400 文件）后，
一次全量构建实测 210 s：扫描网络盘 62 s、读取正文 120 s、jieba 分词 68 s。
每次启动、每次 save、每次轮询都付这个代价，前提已不成立。

## 决策

- 缓存文件 `index.cache`（与 config.json 同目录，pickle，带格式版本与配置指纹，原子写入，
  每次重建成功后写回）。内容：每文件的 mtime、size、正文、块偏移、分词结果、`agent_mtime`，
  以及序列化的 BM25 模型。实测 ≈ 79 MB，加载 ≈ 3.5 s。
- **启动先用缓存立即服务**，后台增量校验：按 `(mtime, size)` 只重读、重分词变化的文件，
  BM25 整体重建（统计量是全局的，21k 块约 4 s），原子替换后写回缓存。
- 轮询、save 后刷新、reindex 一律增量；reindex 另有 `--full` 强制全量。
- 缓存不存在、损坏、指纹不符：告警并全量构建，不阻断服务。

## 备选与取舍

- **先扫描校验再服务**：数据总是最新，但启动仍 ≥ 62 s（扫描本身就慢）。
  选择接受"启动后一两分钟内可能是上次关闭时的内容"，`/health` 的 `verifying` 如实标出。
- **只缓存分词结果、启动重建 BM25**：省 23 MB，启动多 4 s。启动时间是这次改造的目标，选存模型。
- **向量索引**：不相关——本系统没有向量（ADR-0002）。

## 后果

- ADR-0007 中"落盘只会引入不同步故障"的担忧由配置指纹 + 按文件 `(mtime, size)` 校验处理。
- status.json 并入缓存（`agent_mtime`），见 [ADR-0018](0018-edited-by-via-status-file.md)。
- 掉盘时缓存成为该 workspace 唯一的数据来源，见 [ADR-0020](0020-mounted-disk-offline.md)。
