# ADR-0031 · 编辑者登记：`edited_by` 更名 `editor` 并登记写入主体

**状态**：提案 · 2026-10-01（同一轮 grilling 的追加决策；开发细节见 [SPEC-MULTI-USER](../SPEC-MULTI-USER.md)）

## 决策

多人共用后需要回答"这次改动是**哪个用户**做的"——一个二元判定升级为带主体登记：

1. **对外字段更名**：recent 输出里的 `edited_by` **整体替换**为 `editor`。
   recent 是该字段的唯一暴露点（search / get-document 本就不带，不新增）；
   旧字段名不保留、不做兼容过渡。
2. **取值**（判定机制沿用 [ADR-0018](0018-edited-by-via-status-file.md)：
   agent_mtime 判定"写后未被动过"）：
   - **单机形态**（无 `multi_user`）：`agent` / `scan`，语义与从前完全一致；
   - **多人形态**：经 MCP 写入记**路由身份**——普通用户记用户名、管理员记
     管理员名（登记的是动作者，不管写进谁的 source）；访客写入记 `guest`；
     非 MCP 改动仍 `scan`（人手改动无法归因，不推断）。
3. **保留字**：`agent`、`scan`、`guest` 不得用作个人目录名（派生时跳过并警告）
    与管理员名（配置校验拒绝）——否则 editor 的枚举值产生歧义。
   **比较大小写不敏感**（casefold；实施前审查补）：Windows 目录名不区分
   大小写，`Guest` 目录与保留字 `guest` 的歧义在 Windows 上真实存在；
   Linux 上从严统一，两平台行为一致。
4. **缓存**：条目新增 `agent_editor`（与 agent_mtime 并列，跨重启保留）；
   `CACHE_FORMAT` 3→4，**不兼容旧缓存**——升级后首次启动全量重建一次，
   从旧缓存抢救 agent_mtime、editor 记 null（显示为 `agent`），一次性损失接受。

## 理由

- 为什么单字段更名而非加并列字段：agent / scan / 用户名 / guest 是同一个问题
  （"谁动的"）的不同答案，一个字段一个问题；并列字段会让"agent 是谁"永远悬空。
- 为什么 guest 而不是 null：多人形态下"匿名 MCP 写入"与"人手改文件（scan）"
  是两种信号——前者有写入行为可追、后者无主体；null 会把两者混在一起。
- 为什么不兼容旧缓存：字段语义已变（布尔 → 主体登记），兼容层只会让两种
  语义长期共存；万篇级全量重建几分钟一次，成本可接受。

## 后果

- recent 的消费者（工具描述文案、契约测试）同步改名；升级 0.5.0 首次启动
  一次全量重建（万篇级分钟级）。
- 写路径 `run_save` / `run_rename` / `run_replace` 增加 editor
  参数——这是 ADR-0029 "读取类零改动"声明的例外（写路径签名演进）；
  `run_delete` 无标记（文件已删）。
