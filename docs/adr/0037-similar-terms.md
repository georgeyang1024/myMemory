# ADR-0037 · 相似词：save 必填 `similar_terms`，头部 front matter 落盘、同路径词入索引

**状态**：已采纳并实施 · 2026-10-31（0.8.0，定稿形态为 front matter）；
2026-11-02 定稿调整（仍属 0.8.0）：预算 512→128、剔除布尔/纯数字/URL、去引号、支持 YAML 列表、
覆盖时头部按键合并

## 背景

检索内核是 BM25 + jieba 的纯字面匹配（[ADR-0002](0002-bm25-over-vectors.md)）。
"无同义改写"是当年明确接受的损失，给出的缓解办法是：消费方是 LLM，
可以自己改写查询再搜。

实践把这个假设证伪了：**读取端的 LLM 不知道语料当年用的是哪个词**，
改写无从下手。工具说明只能写"搜不到就换原文里可能出现的词"——
一句正确的废话。最疼的失效形态是跨语言词形：记忆写的是"防重放"，
用 `replay` / `nonce` 搜就落空；反之写 `anti-replay` 的段落，
用中文词也搜不到。语料中英混合、人与 AI 双写，这类词形错位每天都在发生。

## 决策

1. **save 新增必填参数 `similar_terms`**：空格分隔的一批相似词——这篇记忆
   **正文里没有、但将来可能被拿来搜它的词形**：同义词、近似词、英文、缩写、简写。
   与 `filename` 同级的严格必填：不传或空串即 `WriteError`，消息给出
   可据以纠正的指引。校验沿用 `filename` 的白名单口径，另加两条：
   词数 ≤ 20、每词 ≤ 64 字符；**拒绝控制字符**——头部格式是硬约束。
2. **落盘形态：文件头部 front matter**（skill metadata 同形态的 `---` 围栏块）：
   `---\nsimilar_terms: 词1 词2 ……\n---`。content 自带的围栏块里如已有
   相似词键，参数行**原位替换**——键是 YAML 列表形态时，键行连同名下列表项行
   整组换成单行（重复的相似词键一并不留）；块内其它键一字不动；
   没有围栏块则新建一个只含该键的块（0.8.0 的平文首行形态已废弃，不做兼容——
   content 里出现时按正文原样保留）。
   **覆盖已有文件时只换正文与 similar_terms**（`corpus.merge_front_matter`，
   在上述装配之前执行）：以旧文件头部为底，旧键全部保留、顺序不变；content
   自带头部时按键合并——同名键（大小写不敏感）用新值整组原位替换（键行 +
   列表项 + 缩进子行，与 YAML 归属一致），旧头部里重复的同名键一并不留，
   新键补在块末；content 头部里的相似词键忽略（以参数为准）。旧文件没有
   合法围栏块（含超 20 行）、或读旧文件失败时，退回按 content 原样装配。
   删除头部某个键只能用 replace。
3. **文件是唯一真理源**：replace 可字面改块内键行；人用编辑器（含 Obsidian
   属性视图）直接改也生效，scan 增量自然拾取；save 整篇覆盖时按新参数重新
   生成键行。与 [[双链]]（[ADR-0035](0035-wikilink-graph.md)）、*记于…* 元信息行的
   "文件里有什么就是什么"惯例完全一致。
4. **入索引：同 `path_tokens` 机制**（[ADR-0012](0012-path-and-term-tokenization.md)
   的泛化，0.8.0 用户拍板扩到**全部短键值**）：`FileEntry` 新增 `fm_tokens`
   （头部 front matter 检索词的分词），每个 chunk 的 BM25 语料 =
   **路径词 + 头部检索词 + 正文分词**——头部键值与文件名同款，"每个 chunk
   都带着"，长文档任意 chunk 位置都能命中。头部检索词的来源与构成：
   - `similar_terms` / `相似词` 键值**必进**，不受预算限制，也不做垃圾值剔除
     （调用方显式给的词，`802` 这类纯数字型号照收）；
   - 块内**其它所有顶层键**（title/keywords/tags/category/description/……
     一律通用，不维护键名清单）的值按以下步骤处理：
     1. **取值**：标量去掉两端成对引号；`[a, b]` 行内列表按逗号拆项；
        值为空且其后紧跟 `- 值` 行的，是 **YAML 块列表**（Obsidian 列表属性、
        skill metadata 的写法），连续列表项都归这个键；每项同样去引号。
     2. **剔除垃圾值**：布尔/null 字面量（true/false/yes/no/on/off/null，
        大小写不敏感）与**纯数字**（含小数点、正负号，不论长短，如毫秒时间戳
        `1738978466000`、`subdoc_depth: 1`）、**整值为 http(s) URL**（去引号后
        `https?://` 开头且不含空白，大小写不敏感；拆词后只剩 https/com/域名/ID）
        不进通道、不占预算。列表逐项剔除；夹在文字里的 URL、其它协议不剔。
     3. **成值**：列表剩下的项用空格拼成一个值，**整组进或整组不进**。
     4. **装预算**：键值**按长度短的优先**进入，累计不超过 **128 字符**
        （`_FM_BUDGET`）——装不下的（含单值超长）整个键留正文，只算 chunk 0；
        空值键（含剔除后为空）不占预算，遮键名但不进词。
   - 不挂在空值键下的游离列表项、缩进的嵌套映射行（`metadata:` 下的子键）
     一律不碰，留在正文——宁可少认。
   - 命中判定（[ADR-0013](0013-term-presence-over-positive-score.md)）
     不需要任何新规则——头部词进了 chunk 语料，"chunk 中确实出现了查询词"
     自动覆盖它。
   被选中的键**整体**（键行 + 名下列表项行；被剔除值的键同样整体遮罩，
   `false`、时间戳、URL 也不留在 chunk 0 正文里）以等长空格遮罩出正文分词
   （[ADR-0035](0035-wikilink-graph.md) 的 `mask_wikilinks` 同手法，保字符偏移），
   由 `corpus.plan_front_matter()` 统一规划：避免与 `fm_tokens` 双重计频，
   也避免 `similar_terms`、`tags` 之类的键名与冒号本身成为高频词条。
   落盘、解析、遮罩三层对"哪个键被选中"给出同一答案，行为完全确定。
5. **键名的识别口径**：认英文键 `similar_terms` 与中文键
   `相似词`——大小写不敏感、容忍 BOM 与全角冒号，其它变体不认。
   键名是给机器的契约，人写错不识别也不报错；中文别称本身可以进词表。
   值认单行（空格分隔）、`[a, b]` 行内列表、YAML 块列表三种写法——
   Obsidian 属性视图把属性设为列表类型时会改写成块列表，不认就等于丢词。
   折叠/字面块（`>` `|`）与嵌套映射不认。
   围栏块形态要求闭合线在前 20 行内出现、块内无空行——宁可少认，不可认错。
   20 行上限在支持列表后**维持不变**（用户拍板）：列表多的头部超限就整块
   按正文处理，与之前一致。
6. **存量兼容**：头部无相似词键的文档（存量全部 + 人编辑器新建的）
   行为与之前完全一致，照常索引照常检索；下次被 save 覆盖时自然补上键行。
   scan 对无键行的文件不警告不报错。0.8.0 平文首行不做兼容（用户拍板：
   强制 front matter）——已按平文落盘的文档在下次 save 前由调用方自行迁移。
7. **文案同步**：`SAVE_DESCRIPTION` 引导"只传正文里没有的词形"——
   正文已有的词本来就搜得到，复读不加分只膨胀；`SERVER_INSTRUCTIONS`
   检索节与 `SEARCH_DESCRIPTION` 从"不做同义改写"改为
   "字面匹配正文 + 头部 front matter 检索词"。save 响应回显
   `similar_terms`（本次写入的词组）与 `replaced_similar_terms`
   （覆盖前旧文档的词组：`[]` = 旧文档没有相似词键，`null` = 新建或读不到旧文），
   让"这次写进去了哪些检索词、覆盖掉了哪些旧词"被看见。

## 考虑过的方案

- **服务端同义词表（内置词林 / 配置 `synonyms`）**：覆盖率 = 词表覆盖率，
  而中英技术词对恰恰是通用词表的弱项；等于在 `domain_terms` 之外再养一张
  要随语料演进的表。同义词知识属于"知道这篇内容在说什么"的模型，
  不属于检索引擎。否决。
- **参数名候选**：`keywords`（太泛，实现中途被推翻）、`similar`（短但语义不完整）、
  `synonyms`（装不下"英文/缩写/简写"的暗示）、`aka`（技术圈味偏重）。
  最终取 `similar_terms`：对 LLM 无歧义。
- **零命中时返回建议词**：把瞎猜换成有依据的猜，但不解决根因——
  建议词仍须来自语料已有词形，而缺口正是语料里没有那个词形。可作未来补充，本期不做。
- **本地嵌入第二路召回 + RRF**（[ADR-0002](0002-bm25-over-vectors.md) 预留的口子）：
  ~100 MB 模型分发、数万 chunk 建向量、持久化向量存储，与"零下载、
  完全离线、秒级冷启动"的定位不成比例。且人手写的旧文档才是无相似词的
  重灾区，向量才是覆盖它们的那条路——**留作确认 similar_terms 覆盖不足后的
  升级路径，本 ADR 不实施**。
- **语料共现自学习扩展**：逻辑上不成立。写"nonce 递增校验"的文档恰恰
  不含"防重放"，待桥接的词对从未共现，共现统计桥接不上。否决。
- **相似词存 sidecar（同 `agent_mtime`，[ADR-0018](0018-edited-by-via-status-file.md)）**：
  相似词要人可见、可编辑、随文件跨设备走（NAS 多端共享场景），
  sidecar 恰恰都做不到。文件头可达。
- **YAML front matter / HTML 注释**（开发中途初评时否决）：当时理由是
  "围栏解析复杂 + 与 Obsidian 属性面板耦合；注释对人不可见"。
  **定稿时推翻此议（用户拍板）**：给既有记忆补相似词的使用场景表明，
  front matter 是本库人与工具已习惯的标准容器——skill metadata 就用它，
  Obsidian 还有原生属性视图可编辑。围栏解析实际只多一条"找闭合线"的规则，
  且本 ADR 已给出"宁可少认不可认错"的收窄口径。HTML 注释维持否决
  （对人不可见）。

### 定稿调整时考虑过的方案（2026-11-02）

起因：用实际语料核对 512 预算的效果。`team` source 的 1086 篇钉钉导出文档
头部全是元数据（`source: "dingtalk"`、`workspace_id`、`node_id`、毫秒时间戳、
`extension: "adoc"`、`import_body: false`……），"短的优先"会让这些值先进通道，
附到每个 chunk 上。

- **预算**：512 → **128**。通道进每个 chunk，预算就是每块的固定附加量；
  128 足够装下标题与几个标签。采纳。
- **相似词计入 128**：否决。相似词已有 ≤20 词的上限，且是调用方显式给的，
  不该被元数据挤掉。
- **短值按长度阈值剔除（如短于 `false` 的 5 字符）**：否决。纯长度会误伤
  短中文（"蓝牙""协议"），中文按 2 宽计也只是缓解。改为按**内容类型**剔除：
  布尔/null 字面量 + 纯数字。采纳。
- **纯数字只剔 ≤5 位**：否决。长数字（时间戳、ID）同样没有检索价值，不论长短都剔。
- **入选顺序改"语义键优先"或"只认白名单键"**：评估时指出，在 team 语料上
  "短的优先"仍会让 `ALIDOC`、`dingtalk`、`workspace_id`、`node_id` 进通道。
  **用户拍板维持"短的优先"**——不维护键名清单的原则优先；残余噪声由
  128 预算与垃圾值剔除共同压低。
- **YAML 多行**：块列表与 `[a, b]` 行内列表采纳；折叠/字面块（`>` `|`）
  与嵌套映射子键不做（语料里少见，解析成本与误认风险更高）。
- **预算 128 → 256**：模拟显示新增空间几乎全被 team 865 篇的 `doc_url` 占去
  （每篇 97→187 字符，URL 拆词全是噪声），换来的只是 skills 29 篇 description
  与 6 个长标题。**用户拍板维持 128**。
- **剔除整值 URL**：与布尔、纯数字同一逻辑（按内容类型，不维护键名清单）。采纳。
- **覆盖时头部的处理**：原先 save 只看 content，旧头部的 title/tags 等键会被
  静默冲掉，响应里也看不出来。考虑过三种：①按键合并（旧头部为底，同名键用新值，
  新键补末尾）；②content 带头部就整块用新的，不带才沿用旧的——只带部分键时
  旧键照样丢；③始终沿用旧头部、丢弃 content 头部——save 无法改任何头部键。
  **用户拍板①**：旧键永不静默丢失；代价是 save 删不了键，删键走 replace。
- **放宽 20 行上限到 60**：team 有 221 篇子文档头部 22–24 行，目前整块不认。
  **用户拍板维持 20 行**——宁可少认。

## 理由

核心判断：**相似词知识在写入时刻最廉价可得**。写入的 LLM 刚组织完
内容，英文、缩写、简写信手拈来；读取端的 LLM 对语料用词一无所知
——这正是现状失效的根源。把 LLM 的语义能力用在写入端，检索端保持
确定性：既修复了 ADR-0002 被实践证伪的缓解假设，又不推翻它
"检索内核零语义"的决定。

顺带的红利：

- 相似词随 md 文件走：NAS 多端共享下，任何设备、任何人写的文档
  都自带相似词，不需要同步任何词表；
- 可审计：get-document 与编辑器里看得见每篇的检索词，
  人可以直接修正 AI 写坏的相似词；
- 机制与 `path_tokens` 完全同构（"代表整篇文档的检索词"），
  实现是既有机制的泛化，不是新发明；
- 头部的 title/keywords/tags 等"身份信息"顺带获得与文件名同款的
  整篇可检索性——skill 文档的描述不再被 chunk 边界挡在检索之外。

## 后果

- **工具契约变化**：save 的入参变多，所有调用方必须传 `similar_terms`。
  MCP 工具 schema 随连接下发，客户端无兼容成本；REST 无写路径，不受影响。
- **文件格式变化**：新建/覆盖的文档头部固定含 `---\nsimilar_terms: …\n---` 围栏块
  （Obsidian 属性视图原生可编辑）——接受的观感代价。
- **TF 膨胀副作用**：`fm_tokens` 进每个 chunk，与路径词同款
  （[ADR-0027](0027-search-scoring-adjustments.md) 后记）；同文档内词频放大，
  跨文档排序仍由 IDF 主导，与查询时加分机制无冲突。头部其它键值
  以 128 字符总预算封顶（每个 chunk 都带，预算即每块的固定附加量，宜小），
  布尔、纯数字与 URL 不计入，膨胀有上界。
- **凑数相似词风险**：生活类记忆可能没有真正的别称，必填会逼出
  主题词复读。工具说明引导"只传正文没有的词形"缓解，残余风险接受。
- **`index.cache` 兼容**（[ADR-0019](0019-index-cache-incremental.md)）：
  `FileEntry` 语料变了就必须递增缓存格式（教训见 0.7.0 先例）——
  本次从 5 一路改到 **10**，其中 6/7/8/9 是未随版本发布的开发中间形态
  （平文首行→仅 similar_terms 键行遮罩→全部短键值、预算 512→预算 128 与剔除布尔/数字）；**升级后首次启动全量重建一次**
  （实测语料秒级完成）。
- **长度口径**：`max_create_chars` 校验的是 content 去掉头块后的正文；
  落盘后的 `char_count` 含头块与结尾换行，与现状同口径。
- **残余缺口**：人手写的旧文档在被人补头部键或被 save 覆盖之前，
  同义词召回与之前一样缺失。这是接受的损失，兜底是升级路径
  （本地嵌入第二路召回）而非本 ADR 的范围。
